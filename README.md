# LLM Router

複数のGPUサーバで動くLLM推論サービス（vLLM・llama.cpp）を、1つのOpenAI互換APIにまとめるRouterです。利用者間の公平なキューイング、同時実行数の制御、稼働状況の可視化を行います。

## 背景

### GPUはたくさんあるのに、動かせるLLMは少ない

私たちの研究室には、GPUを積んだマシンがかなりの台数あります。世代も構成もばらばらで、GPU 1枚のマシンもあれば2枚挿しのマシンもあり、メモリも24GBのものから大容量のものまでさまざまです。研究ではこれらのマシンにLLMを立てて、vLLMやllama.cppで推論サーバとして使っています。

ただ、最近のオープンウェイトモデルはどんどん大きくなっています。たとえば30B級のモデルを16bit（1パラメータあたり2バイト）でそのまま載せると、重みだけで約60GBのGPUメモリを使います。推論中はここにKVキャッシュが加わり、文脈が長くなったり同時リクエストが増えたりするほど、さらに多くのメモリが必要になります。結局、大きめのモデルだとGPUを1〜2枚積んだマシン1台に載せられるのは1モデル程度で、24GBクラスのGPUでは4bit程度まで量子化しないと載りません。

つまり、マシンの台数自体は多くても、研究室全体で同時に動かせるLLMの数は意外と限られます。

### 誰がどこで何を動かしているのか分からない

研究室のメンバーは、みんなが同じモデルを使うわけではありません。研究テーマによって使いたいモデルは違いますし、学会や論文の締め切りが近い繁忙期になると、限られたモデルにリクエストが集中します。すると待ち時間が発生したり、推論が極端に遅くなったり、最悪の場合は推論サーバが止まってしまったりします。

さらに困っていたのが、「どのマシンの、どのポートで、何のモデルが動いているのか」が一目で分からないことでした。

これまでは、モデルを確認するたびに次のような作業をしていました。

1. 各マシンにSSHでログインする
2. `docker compose ps`などで、どのポートに何のモデルが立っているかを一つずつ確認する
3. 使われていないモデルがあれば落とし、次に使いたい人の要望を聞いて別のモデルを立てる
4. ログアウトして、次のマシンへ

複数のマシン・複数のポートに散らばったモデルを、人が一つずつ見て回るしかなく、研究室全体の状況を一元的に把握する手段がありませんでした。どのモデルがどれくらい使われているのか、いつ混んでいるのかといった稼働状況も、記録として残っていませんでした。

### これから先を見据えて

マシンは今後も増える予定で、LLMもさらに大規模で複雑になっていきます。そうなると、どのマシンにどのモデルを置くかを、その時々の研究の状況や急ぎのニーズに合わせて柔軟に変えていく必要があります。そのためには、まず全体が見えていること、そして稼働状況を中長期でモニタリングして判断材料にできることが欠かせません。

そこで、散らばった推論サーバを一か所から見渡せて、リクエストを公平に順番待ちさせられて、利用状況を継続的に記録できる仕組みとして、このRouterを作りました。

## 主な機能

- **OpenAI互換API**：Chat Completions、Streaming、tool callingを中継。既存のOpenAIクライアントがそのまま使える
- **公平なキュー**：Endpointごとの同時実行上限と、利用者間のRound-Robin
- **公開ステータスページ**：ログイン不要で、各サーバの稼働モデル・混み具合・GPU使用率を確認できる
- **管理画面**：接続先・モデル名・利用者・APIキーの管理、利用履歴の確認
- **負荷試験**：GuideLLMでサーバの処理能力を測定し、同時実行上限を決める材料にする

## 構成と設計のポイント

```text
利用者（OpenAI互換クライアント）
  └─ Router：認証 → モデル名の解決 → Endpoint別キュー → 推論サーバ（vLLM / llama.cpp）
       ├─ Web画面（公開ステータス / 管理画面）
       ├─ SQLite（設定・利用履歴・測定結果）
       └─ CPU runner（GuideLLM負荷試験）
```

- **一人に独占させないキュー**：利用者ごとにFIFOのキューを持ち、待っている利用者を順番に回して処理します。大量のリクエストを送った人がいても、他の人の待ち時間が極端に伸びません。
- **上限は測定に基づいて人が決める**：同時実行上限は負荷試験の結果を見て管理者が設定します。
- **中継に役割を絞る**：モデルの起動・停止は行わず、既存の推論サーバの前に置くだけで使えるようにしました。
- **シンプルな単一プロセス構成**：想定規模は研究室・小規模チームです。SQLiteと単一プロセスで動かし、キューの状態を1か所で一貫して管理します。
- **見せる情報と隠す情報を分ける**：混み具合は誰でも見られるようにして、APIキー・接続先URL・利用者情報は管理者だけが見られるようにしました。プロンプトや生成結果は保存しません。

## 技術スタック

- バックエンド：Python、FastAPI、SQLite（aiosqlite）
- フロントエンド：React、TypeScript、Vite
- 実行環境：Docker Compose
- テスト：pytest、Playwright

## クイックスタート

```bash
python3 scripts/prepare_runner.py
docker compose build router runner
docker compose run --rm --no-deps router admin --username admin
docker compose up -d router runner
```

- 公開ステータス：http://127.0.0.1:18080/
- 管理画面：http://127.0.0.1:18080/admin

推論APIは、Base URLを`http://127.0.0.1:18080/v1`にして、管理画面で発行したAPIキーを使います。

```bash
curl http://127.0.0.1:18080/v1/chat/completions \
  -H "Authorization: Bearer $ROUTER_API_KEY" \
  -H 'Content-Type: application/json' \
  -d '{"model":"my-model","messages":[{"role":"user","content":"こんにちは"}]}'
```
