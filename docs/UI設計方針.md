# UI設計方針

更新日: 2026-09-19

ユーザー指定: 白・黒・グレーでシンプルに統一し、カードを多用しない。管理者が表から状態を把握し、その場で必要な操作へ進める画面を作る。

## 1. 共通レイアウト

- 左に細い固定ナビゲーション、右に広い本文領域を置く。
- 本文は「画面名と主要操作 → 検索・絞込み → 表／グラフ → 詳細」の順に配置する。
- 白背景と細いグレーの区切り線を基本とし、各情報を角丸の箱に囲まない。
- 数値の概要は1行の横並びテキストか集計表で表示する。大きなKPIカードを並べない。
- 詳細画面は見出し、項目と値の行、タブ、表で構成する。編集はまとまったフォームとして表示する。
- 色付きバナー、グラデーション、装飾イラスト、強い影、大きな余白を占める歓迎エリアは使わない。

## 2. 視覚仕様

| 要素 | 実装基準 |
| --- | --- |
| 背景 | 基本は白。ナビゲーションや表ヘッダーは薄いグレー |
| 文字 | 本文・見出しは黒に近いグレー、補助情報は可読性を保った中間グレー |
| 境界 | 薄いグレーの1px線を基本。見出しと余白でも情報を分ける |
| 操作 | 主操作は黒地・白文字、通常操作は白地・境界線、補助操作はテキスト |
| 角丸・影 | 角丸は小さく、影は原則なし。カード風の浮き上がりを作らない |
| 数値 | 比較しやすい桁揃え、単位と集計期間を明記。表内の数値は右寄せ |
| 状態 | 「正常」「不健全」「未確認」「無効」「試験中」等の文字と記号で区別。色だけに頼らない |
| グラフ | 黒・グレーの線、実線／破線、記号、凡例で区別。系列が多い場合は選択や分割表示を使う |
| フォーカス | キーボード操作時は明瞭な黒系の輪郭を表示 |

色はCSS等の共通トークンにまとめ、画面ごとに独自の配色を追加しない。状態の点に限り、正常・完了は緑、接続失敗・エラーは赤、待機・実行中・未確認等は黄色、無効・取消はグレーを使う。状態の文字を併記し、色だけに頼らない（追加のユーザー指定を反映）。

## 3. 画面構成

| 画面 | 主な表示 | 主な操作 |
| --- | --- | --- |
| ログイン | 設定したロゴ・組織名・説明文、管理者のログインフォーム | ログイン |
| 概況 | 実行中・待機中・直近件数の集計行、Endpoint一覧、時系列グラフ | 対象の詳細へ移動、期間変更 |
| サーバ・Endpoint | 名前、所属Server、URL、backend、状態、モデル、実行数／Capacity、待機数、最終確認 | 登録、編集、有効／無効、接続確認 |
| Endpoint詳細 | 基本情報の項目行、Alias表、性能・利用量グラフ、直近要求 | Capacity編集、試験画面へ移動 |
| Model Alias | Alias、上流モデル、Endpoint、有効状態 | 追加、変更、削除 |
| リクエスト | ID、User、Alias、状態、受付時刻、待機時間、処理時間、トークン数 | 検索、絞込み、詳細、キャンセル |
| 利用者・API Key | 利用者一覧、利用量、キー名・発行日・失効状態 | User作成、キー発行・失効 |
| 負荷試験 | GuideLLM条件フォーム、実行履歴、進捗、結果比較表・グラフ | 事前計数、開始、停止、設定複製・JSON入出力、JSON／CSV／HTML出力 |
| 設定 | ロゴ文字・組織名・説明文、監視周期、キュー待機期限、保持期間等の項目行 | 編集、保存 |

ServerとEndpointは画面上で近くに配置しても、データ上は別の概念として扱う。初期の一般利用者向けポータルやチャット画面は作成範囲に含めない。

## 4. 情報と操作の扱い

- 一覧は表を基本とし、検索・フィルタ・並び替え・ページングで必要な行を探せるようにする。
- 小さい画面でも主要操作に到達できるようナビゲーションを折り畳み、幅広い表は横スクロールで表示する。スマートフォンでカードへ自動変換することを前提にしない。
- 5秒周期の更新で表のスクロール、選択、入力途中のフォームをリセットしない。
- 未取得は「未取得」または「—」と説明で示し、0に置き換えない。更新時刻を表示する。
- 稼働状態と管理者による有効／無効を混同しない。
- API Keyの平文表示は発行時のみ。上流Credentialは登録・更新できるが、保存後に再表示しない。
- プロンプト、生成本文、ツール引数・実行結果をリクエスト詳細へ表示するために保存しない。
- 負荷試験の結果に「合格」「推奨」「最適」等の判定を付けない。測定条件・数値・欠測・中止理由を示す。
- 上流のコンテキスト長は観測情報として表示可能だが、Routerの制限値を入力するフォームにはしない。
- 接続後の応答待ちタイムアウトを設定するフォームは作らない。キュー待機期限は別項目として意味を説明する。
- 操作に失敗した場合は対象・理由・再操作の可否を近くに表示し、入力内容を失わせない。

### 負荷試験の入力と表示名

基本の入力選択は「公開データセットから選ぶ」「独自ファイルを使う」の2種類。公開データはGSM8K、CNN/DailyMail、その他のHF IDを指定できる。取得設定の選択と実データの取得を区別し、選択だけでダウンロードしない。合成入力とTraceは「詳細な入力設定」にまとめる。Tokenizerは入力データ設定の後に置き、対象モデルとの対応を明示する。

入力側の計数・指定出力長・サーバusageを分け、欠測を目標値で埋めない。旧試験の複製は元の入力方式を保持する。事前確認で本文は表示せず、件数と計数結果を示す。

設定の「ロゴと組織名」でロゴ文字（最大12文字）、組織名（最大60文字）、説明文（最大100文字）を変更する。保存結果はログイン画面・サイドバー・ブラウザタイトルへ反映する。既定はllm／Labだが、demoやDEMOへの変更にコード編集は不要。

## 5. UIの完了条件

1. 全画面が白黒グレーを基調とする共通配色・文字・境界・操作部品を使い、状態の点のみ定義済みの緑・赤・黄色を使用する。
2. 一覧・詳細の主要情報が表と項目行で読め、カードの反復や装飾的なKPIタイルがない。
3. 状態・系列・操作可能性が色だけに依存せず判別できる。
4. キーボードでログイン、登録、検索、編集、キャンセルへ到達できる。
5. ロード中、空一覧、未取得、通信失敗が区別され、架空の値で埋められていない。
6. UIから登録した設定が実際のAPI・キュー・試験へ反映され、操作の完了と失敗が確認できる。

UIの実装は [開発計画](開発計画.md) の各工程に組み込み、実データで確認しながら整える。
