# 運用手順

更新日: 2026-09-19

現在の開発環境はDocker Composeへ切替済み。[Docker運用](Docker運用.md) を参照。以下の直接起動手順はDockerを使わない場合に用いる。

## 1. 開発ホストでの起動

リポジトリのルートを作業ディレクトリとして使う。インストールとビルドは [README](../README.md) を参照。

```bash
.venv/bin/llm-router serve --host 127.0.0.1 --port 18080
```

初期は1 workerのみ。複数workerを起動するとそれぞれに実行枠を作ることになるため、データディレクトリのロックで拒否する。

設定は`.env`または環境変数で渡す。例は`.env.example`にあり、上流Credentialは管理画面で登録する。

| 設定 | 既定値 | 意味 |
| --- | --- | --- |
| `LLM_ROUTER_DATA_DIR` | `.local/data` | DB、暗号鍵、排他ロック、登録データセット・Tokenizer |
| `LLM_ROUTER_HOST` | `127.0.0.1` | 待受アドレス |
| `LLM_ROUTER_PORT` | `18080` | 待受ポート |
| `LLM_ROUTER_SECURE_COOKIES` | `false` | HTTPS配備時は`true` |
| `LLM_ROUTER_PUBLIC_ORIGIN` | 未指定 | リバースプロキシを使う場合の公開オリジン |
| `LLM_ROUTER_ENCRYPTION_KEY` | 未指定 | 任意のFernet鍵。未指定時はデータディレクトリへ自動生成 |
| `LLM_ROUTER_RUNNER_URL` | `http://127.0.0.1:18083` | CPU用GuideLLM runnerの接続先 |
| `LLM_ROUTER_RUNNER_KEY_FILE` | `.local/runner.key` | Routerとrunnerで共有する内部認証キーのファイル |
| `LLM_ROUTER_BENCHMARK_ROUTER_URL` | `http://127.0.0.1:18080/v1` | runnerから到達できるRouterの推論URL |

開発ホストの`127.0.0.1:18020`は、別コンテナ・別ホストのlocalhostとは異なる。配備場所を変えたら、Routerから到達できる上流Base URLに更新する。

SSH接続先で運用する場合は、手元にポートを転送して管理画面を利用できる。

```bash
ssh -L 18080:127.0.0.1:18080 YOUR_DEVELOPMENT_HOST
```

## 2. 管理者・利用者キー

```bash
.venv/bin/llm-router admin --username admin
```

管理者パスワードを変更すると既存管理者セッションは失効する。自動セットアップでは`LLM_ROUTER_INITIAL_ADMIN_PASSWORD`環境変数も使用できるが、値はソースや文書に残さない。

利用者キーは管理画面または次のCLIで発行する。平文は発行時のみ表示する。

```bash
.venv/bin/llm-router key --user researcher --name research-script
```

キーの失効は新規要求に適用する。利用者の無効化では待機要求も終了する。実行中要求を止める場合は、リクエスト画面でキャンセルする。

## 3. 監視・変更・再起動

- 接続先を登録したら接続確認を行い、上流モデル名とAliasを対応させる。
- Capacityの増減は接続先詳細で設定する。減少時に実行中の要求を強制終了しない。
- URLや上流キーを変更する場合は、対象の待機・実行中要求の終了を待つ。
- アプリ停止時は既存接続が終了または中断する。自動再送しないため、利用者は結果を確認して再実行する。
- 異常終了前に実行中だったEndpointは再起動後に受付を保留する。上流の残存推論を確認し、接続先詳細の「受付を再開」を操作する。
- 正常なヘルスチェックは、再起動前の推論がすべて終了した証明にはしない。

## 4. 負荷試験

推奨起動方法は[Docker運用](Docker運用.md)のCompose。Routerだけを直接起動してもGuideLLM runnerは起動しない。負荷試験にはCPU依存関係を固定したrunner、内部認証キー、入力資産の共有が必要になる。

1. 保守時間に対象モデルと直接接続／Router経由を選ぶ。
2. 公開データセットまたは独自ファイルを指定する。合成入力・Traceは詳細設定を開く。
3. 対象モデルのTokenizerを指定し、「入力を事前確認」で計数する。HFデータとTokenizerはこの時点で取得される場合がある。推論は実行しない。
4. 出力長、負荷方式、要求数または投入時間を指定して開始する。
5. 進捗・結果を確認し、必要なら停止、設定複製、比較、結果出力を行う。

Endpoint直接はCapacity制限を使わず、Router経由は現在のCapacityとキューを通る。試験中は対象の通常受付を停止し、既存実行中要求の終了を待つ。投入時間の終了後も送信済み要求の応答を待つ。

停止・失敗時も取得済みの結果を保持する。欠測は「—」で表示し、指定長とサーバusageを区別する。合否や推奨値は付けず、Capacityは接続先詳細から管理者が設定する。操作と測定値の定義は[GuideLLM運用](GuideLLM運用.md)を参照。

## 5. バックアップと復旧

```bash
.venv/bin/llm-router backup --output .local/backups/backup-YYYYMMDD
```

SQLiteのバックアップAPIを使い、稼働中でも整合したDBコピーを作成する。ファイル管理の暗号鍵と登録済み`datasets`・`tokenizers`ディレクトリも一緒に保存する。環境変数で渡した鍵は別途保管する。

復旧時はRouterを停止し、別のデータディレクトリへ`router.sqlite3`と対応する`encryption.key`、`datasets`・`tokenizers`を配置し、`LLM_ROUTER_DATA_DIR`を切り替えて起動する。元のディレクトリは確認が終わるまで保持する。DBだけ復旧して新しい暗号鍵を生成しない。

復旧前の接続は再現しない。実行中だった要求は中断として扱い、Endpointの受付再開を確認する。暗号鍵とDBには所有者限定の読み取り権限を設定する。復旧先のrunnerにも同じ入力資産をマウントし、Routerとrunnerの内部認証キーを一致させる。runnerキャッシュと一時ジョブ領域はDBバックアップの対象外。

## 6. テスト環境

backendテストは一時DBと模擬上流を使う。Playwrightは`18081`にテスト専用Routerを起動する。通常の開発Router（`18080`）のDBと実GPUを使わない。GuideLLMのE2EにはCPU runnerとgpt2 Tokenizerが必要。独自ファイルのテストでは専用UUIDの資産だけをrunnerのマウント先へ一時コピーし、終了後に削除する。既存資産は上書きしない。

この開発ホストのUbuntu 20.04では、Playwrightのプラットフォーム判定に明示指定が必要だった。今回の環境では次の設定で実行する。

```bash
cd web
export PLAYWRIGHT_HOST_PLATFORM_OVERRIDE=ubuntu22.04-x64
export PLAYWRIGHT_BROWSERS_PATH="$PWD/../.local/browsers"
npx playwright install chromium
npm run test:e2e
```

実機の少数リクエスト検証は`scripts/smoke_live.py`。ローカル初期管理者ファイルを読み、検証用キーを一時発行し、終了時に失効させる。実モデルのスループット評価を代替するものではない。

## 7. リバースプロキシを追加する場合

初回実装は直接配信する。後からHTTP中継を追加する際はSSEのバッファリングと応答読み取りの期限を確認する。中継製品の既定値で長文prefillや無通信時間を打ち切る構成は、本要件の「応答待ち期限なし」を満たさない。

公開オリジンとSecure Cookieを合わせて設定し、推論の本文・認証ヘッダーをアクセスログへ含めない。

## 8. 同じホストのハードウェア監視

NVIDIAドライバの`nvidia-smi`が使えるLinuxホストでは、付属の読み取り専用Exporterを起動できる。

```bash
.venv/bin/llm-router hardware-exporter --port 18082
```

このプロセスは`127.0.0.1`にだけ待ち受ける。管理画面の「接続先 → サーバ → 編集」でMetrics URLを`http://127.0.0.1:18082/metrics`に設定すると、通常の監視周期でGPU使用率、VRAM使用量・空き、温度、電力、RAM、CPUロード平均を保存する。別ホストのGPUはこのURLでは監視できない。

CPUロード平均はCPU使用率とは異なる。GPU・RAMはホスト全体の値で、Router以外の処理も含む。取得できないGPU指標は欠測とし、`llm_router_gpu_scrape_success`でGPU取得失敗を確認できる。サーバ画面には最新値と直近1時間（最大500観測）の履歴グラフを表示する。

vLLMのMetrics URLはEndpoint編集画面で別途指定する。今回の開発環境では`http://127.0.0.1:18020/metrics`を設定した。KVキャッシュ等の上流指標とGPU全体の指標を区別する。

## 9. 長文・長時間の試験

詳細設定の合成入力ではTokenizerに基づく入力トークン数を指定する。出力長は生成上限であり、EOSで短くなる。対応する上流で「EOSを無視」を選ぶと試験要求に`ignore_eos=true`を指定できる。通常推論の設定は変更しない。

チャットテンプレート等により入力側の計数と上流usageには差が生じる。上流のコンテキスト制約を確認し、結果の実測値を読む。既知の最大長と合成入力に対する事前確認だけでは、すべての入力方式・テンプレートの超過を検出できない。切り詰めや自動再送は行わない。

旧エンジンでの120k入力・長時間生成の測定は[実機測定結果](実機測定結果.md)に当時の条件で残す。GuideLLMで同規模の実GPU再測定は未実施。繰り返す入力には上流のキャッシュ効果が含まれ得る。

## 10. ロゴ・組織名の変更

管理画面の「設定 → ロゴと組織名」でロゴ文字、組織名、説明文を保存する。llm／Labは初期値で、demoやDEMO等へ変更できる。ログイン画面・サイドバー・ページタイトルにも反映する。起動コマンド、環境変数の`LLM_ROUTER_`接頭辞、Dockerサービス名の変更は不要。
