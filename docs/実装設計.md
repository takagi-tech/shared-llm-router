# 実装設計

更新日: 2026-09-19

## 1. 採用構成

| 領域 | 実装 |
| --- | --- |
| backend | Python 3.12、FastAPI、Uvicorn。1 workerで稼働 |
| 上流中継 | HTTPX AsyncClient。接続5秒、read/write/poolは期限なし、環境プロキシ非使用、リダイレクト追従なし |
| DB | SQLite、WAL、aiosqlite。スキーマは`PRAGMA user_version`で管理 |
| frontend | React、TypeScript、Vite。静的ビルドを同じbackendから配信 |
| 管理者認証 | Argon2パスワードハッシュ、ランダムなサーバ側セッション、HttpOnly/SameSite Cookie、CSRF検証 |
| 利用者認証 | 高エントロピーのランダムBearerキー。SHA-256ハッシュのみ保存 |
| 上流Credential | Fernetで暗号化。鍵は環境変数または所有者限定ファイル |
| 試験実行 | GuideLLM 0.7.3を固定したCPU用runner。内部キー認証、ジョブごとのworkerプロセス |
| テスト | pytest、模擬上流、Playwright、実モデルの少数リクエスト検証 |

初期は1台に配置し、DBやSchedulerを別サービスに分散しない。データディレクトリの排他ロックで、同一DBに対する複数Schedulerの起動を拒否する。

HTTPXの通常の読み取りタイムアウトを無効化し、ライブラリの既定値による中断を避けている。監視用HTTPクライアントだけは5秒の期限を持つ。[HTTPXのタイムアウト仕様](https://www.python-httpx.org/advanced/timeouts/)

## 2. 処理と状態管理

認証→Alias解決→Request保存→Endpoint別キュー→上流接続→応答中継→計測確定の順で処理する。

- Schedulerの操作は単一イベントループ上で同期的に行い、キューを変更する途中に`await`を置かない。
- UserごとにFIFOを持ち、待機中UserをRound-Robinで巡回する。
- 上流接続開始からStreamingの終了・上流接続のクローズまで実行枠を保持する。
- 待機中キャンセルはキューから除去。実行中キャンセルは中継タスクと上流接続を終了する。
- 終了状態・メトリクス確定と枠解放は一度だけ行う。
- クライアントへの送信はバックプレッシャーに従い、Streaming全体を蓄積しない。

状態は`queued`、`running`、`completed`、`failed`、`cancelled`、`interrupted`。エラー理由を本文とは別のコードとして保存する。

入力の`model`だけをAliasから実モデル名へ解決する。他の入力パラメータを補完・上書きしない。SSEは元のイベントを中継し、計測用に別途観測する。ツール自体は実行しない。

## 3. IDとキャンセル

- Router内部IDはUUIDを発行し、応答の`X-Request-ID`で返す。
- クライアントは任意の`X-Request-ID`を要求時に指定可能。内部IDと別に、User単位の一意なクライアントIDとして保存する。
- クライアントIDは英数字と`_.:-`、1〜128文字。履歴が保持される間は同じUserの重複を409で拒否する。
- 応答待ち中のキャンセルは`/v1/requests/by-client-id/{id}/cancel`を使う。
- 内部IDを取得した後は`/v1/requests/{id}/cancel`を使える。
- 本人のBearerキーまたは管理者セッションのみ操作できる。他Userの要求の存在を返さない。

受付前の取消は404となるため、クライアントは受付状況を照会するか、元の接続を閉じる。ID指定は推論の自動再送や冪等な再実行を保証するものではない。

## 4. Registryの変更と障害

- 無効化: 新規要求を拒否し、待機要求を理由付きエラーで終了。実行中要求は継続。
- URL・Credential等の変更: 待機／実行中要求がある間は409。終了後に変更し、健康状態を未確認に戻す。
- Alias編集・削除: 関連要求または試験の終了後に操作する。
- Capacity減少: 実行中要求を追い出さず、実行中数が新しい上限を下回るまで新規実行を待たせる。
- Endpoint削除: 待機／実行／試験がないときにアーカイブし、Aliasを無効化する。履歴は維持する。
- ヘルスチェック: 初回成功で正常、連続3回失敗で不健全、復旧は連続2回成功が初期値。
- 再起動: 未終了要求を`interrupted`にし、再送しない。実行中だったEndpointは`recovery_required`として受付を保留。管理者が上流の残存処理を確認して画面から再開する。

独立Endpointは独立した実行枠を持つ。複数Endpointが同じGPUを共有する場合の自動的な総容量制御は初回版では行わず、管理者が配分したCapacityで運用する。

## 5. データと計測

DBには管理者・セッション、User・API Key、Server・Endpoint・Alias、Requestメタデータ、1分集計、ヘルス・リソース時系列、Benchmark・段階別結果・進捗、登録データセット／Tokenizerのメタデータ、設定を保存する。明示的に登録した入力ファイルとTokenizerは別資産としてデータディレクトリに保存する。

- 受付・開始・終了などはUnix時刻、時間差は単調時計で測定する。
- 通常要求の本文・ツール定義・引数・結果をDBに保存しない。処理中のメモリからは終了時に解放する。
- トークン数は上流のusageから取得。Streamingでusageが返らない場合は欠測とする。通常要求へ`stream_options`を勝手に追加しない。
- TTFTは最初の生成内容またはツール名・引数等を含むイベントまで。非Streamingは欠測。
- 集計は終了時刻の1分バケット単位。成功した要求の遅延分布と、全終了状態の件数を分ける。
- 分位値は合算可能なヒストグラムで保存・集計し、画面で近似と表示する。上限を超える値は欠測表示とオーバーフロー件数で区別する。
- 明細30日、集計・ヘルス・リソース時系列90日が初期保持期間。保持処理は約1時間ごと。
- GPU等は任意のPrometheus形式Metrics URLから既知の数値指標のみ収集する。未設定・取得失敗を0と扱わない。

## 6. 負荷試験

新規試験はGuideLLM 0.7.3をCPU用runnerで実行する。Routerは排他・認証・設定検証・履歴を管理する。旧`router-http-v1`の結果は旧エンジンの履歴として保持する。

- `engines.py`のregistryがエンジン版、設定schema、フォームID、adapterを提供する。現在の新規選択肢はGuideLLMのみ。フォームは`BenchmarkForm.tsx`で選択する。
- 基本入力は公開Hugging Faceデータセットまたは独自JSON／JSONL／CSV。GSM8KとCNN/DailyMailの取得設定を用意する。選択だけではダウンロードせず、事前確認・実行時に取得する。
- 合成入力とTraceは詳細設定。合成入力はFakerのダミー文章を指定トークン数に調整する。入力TokenizerはHF ID／revisionまたはローカルZIPを指定し、対象モデルとの一致を管理者が確認する。
- 逐次、固定同時実行、固定RPS、Poisson、Throughput、Sweep、Replayの7方式。要求数または投入時間で各段階の投入を終了し、送信済み要求の応答は期限なしで待つ。
- Endpoint直接は通常Capacityを迂回する。Router経由は一時キーで通常HTTP経路・Capacity・待機列を通る。試験中は対象の通常要求を拒否し、待機要求を終了させ、実行中要求の終了を待って開始する。
- 停止、エラー、Routerとの監視接続断を処理する。workerと子プロセスを回収し、一時キーを失効する。上流処理の残存を否定できない場合は受付を保留し、管理者が確認して再開する。
- 入力側Tokenizer計数、指定出力長、サーバusageを区別する。usageがないトークン実測値は欠測とし、指定長で埋めない。GuideLLMの補完値はJSONの`native`に区別して残す。
- TTFT・E2E・TPOT・ITLはGuideLLM集計。token/sはトークン到着列の時間加重平均で、総トークン数÷全経過時間とは異なる。旧エンジンと指標定義を混同しない。
- 設定複製・JSON入出力、同一エンジン／版の比較、JSON／CSV／HTML結果出力に対応。本文や秘密値を結果へ保存しない。登録済み入力資産とrunnerキャッシュは別管理する。
- 合否判定、推奨Capacity、自動適用は行わない。試験条件を通常要求へ流用しない。

操作・制限・復旧は[GuideLLM運用](GuideLLM運用.md)、プロセス配置は[Docker運用](Docker運用.md)を参照。

## 7. APIの区分

| 区分 | 主なパス | 認証 |
| --- | --- | --- |
| 推論 | `/v1/models`、`/v1/chat/completions` | Router API Key |
| 本人の要求 | `/v1/requests/{id}`、`/v1/requests/by-client-id/{id}`と各`/cancel` | Router API Key |
| 管理者認証 | `/api/auth/login`、`/session`、`/logout` | パスワード／Cookie |
| Registry | `/api/admin/servers`、`/endpoints`、`/aliases` | 管理者セッション、変更時CSRF |
| 利用者 | `/api/admin/users`、`/users/{id}/keys`、`/keys/{id}` | 同上 |
| 観測 | `/api/admin/requests`、`/metrics`、`/resources/{kind}/{id}` | 同上 |
| 試験 | `/api/admin/benchmarks`、`/{id}`、`/{id}/stop` | 同上 |
| 設定 | `/api/admin/settings` | 同上 |
| 表示名 | `/api/branding` | 認証不要。ロゴ文字・組織名・説明文の3項目だけを返す |

詳細スキーマは管理者ログイン後の`/api/admin/openapi.json`で取得可能。推論本文は独自の固定パラメータ集合に縮めず転送するため、OpenAPIでは詳細のすべてを表現しない。


## 8. 表示名と主な実装箇所

設定の`logo_text`、`organization_name`、`workspace_description`を保存し、ログイン画面・サイドバー・ページタイトルへ反映する。既定は`llm`／`Lab`／`研究室の推論基盤`。demoやDEMOへの変更にコード編集は不要。組織ごとに別配置する想定で、複数組織を同一DBで分離する機能ではない。

| 実装 | 責務 |
| --- | --- |
| `app.py`、`admin.py`、`auth.py` | API入口、管理操作、認証 |
| `scheduler.py`、`proxy.py` | 実行枠と公平性、上流中継 |
| `monitor.py`、`metrics.py` | 接続・モデル監視、集計 |
| `db.py`、`schema.sql` | 永続化とスキーマ移行 |
| `benchmark.py`、`benchmark_api.py` | 試験の排他・状態・資産・結果API |
| `runner.py`、`guidellm_worker.py`、`guidellm_adapter.py` | CPUジョブ管理、GuideLLM実行と結果変換 |
| `web/src/branding.tsx` | 共通ロゴと表示名の反映 |

現在の監視では登録モデルが上流一覧にない場合も`registered_model_missing`としてEndpointの不健全判定に含める。通信到達性とモデル利用可否を独立した健康状態として扱う設計は未実装。`/v1/models`は有効な登録Aliasの一覧であり、即時の推論成功を保証しない。
