# GuideLLM統合計画

2026-09-19整理・実装。以下は合意した設計方針。実装済みの操作・制約・検証方法は[GuideLLM運用](GuideLLM運用.md)を参照。EOS終了理由の個別保存は未実装。コンテキスト上限の事前確認は上流がmax_model_lenを公開し、合成入力を使う場合に限る。

## 方針

- 当面、新規試験のエンジンはGuideLLMだけにする。
- アプリから設定、実行、進捗確認、停止、結果閲覧、比較、再実行、エクスポートまで完結させる。
- 将来、独自試験や別の既存ツールを追加できるよう、フォームと実行処理をエンジン単位で拡張する。
- 測定値を示す。合否判定、推奨Capacity、Capacityの自動変更は行わない。
- 初期対象は既存のOpenAI互換テキスト生成サーバ。GuideLLMの全バックエンド・マルチモーダル機能を一括実装する意味ではない。

## 画面と操作

試験一覧 → 新規試験 → 条件確認 → 実行詳細 → 結果。過去の設定を複製して再実行できる。
既存の白黒グレー・表中心の画面を継承する。

| フォーム区分 | 項目・挙動 |
| --- | --- |
| 共通設定 | 試験名、メモ、エンジン、登録済み対象、直接接続／Router経由 |
| モデル・トークン計数 | 対象モデル、対応するTokenizer、Tokenizerの版。取得状況・計数方法を表示 |
| 入力データ | 基本は公開HFデータセット／独自ファイル。合成入力と到着時刻・長さのトレースは詳細設定 |
| 入出力条件 | 入力・出力の目標長、分布、サンプル数、乱数seed、EOSの扱い、生成パラメータ |
| 負荷条件 | 逐次、固定同時実行、固定RPS、Poisson、Throughput、Sweep、Replay。選択した方式の項目だけ表示 |
| 終了条件 | 各段階の要求数または負荷投入時間、エラー時の停止条件。適用単位を明示 |
| 詳細設定 | GuideLLM固有設定を構造化して編集。検証済み設定のJSON表示・入出力 |

基本フォームを入口にし、詳細設定は折りたたむ。任意のシェルコマンドを入力する方式にはしない。
データセットでは対応形式・列割り当て・利用件数を選び、実行前に計数結果だけを確認できるようにする。

### 入力長・出力長の意味を明確にする

旧フォームの「合成入力の単語数」は廃止済み。対象モデルに合ったTokenizerで生成・計数する。
モデル名がGGUF名や独自aliasの場合はTokenizerを別途指定でき、無関係なTokenizerへ黙って代替しない。

結果には「設定した目標値」「生成した入力の計数値」「サーバが返したusage」を区別して保存・表示する。
チャットテンプレート等によりサーバ上の入力長が増える場合があるため、指定値との完全一致を保証しない。
usageがない場合は欠測と推定値を明示し、サーバ実測値として扱わない。

出力長はEOSによる早期終了があり、上限指定だけではその長さの生成を保証しない。
通常生成と、対応バックエンドでのEOS無視による長時間生成を明示的に選ぶ。
未対応パラメータは事前に検出できる範囲で検証し、未確認ならその状態を示す。
コンテキスト長の超過が判明した場合は開始前に知らせ、入力を自動切り詰めしない。
seedとデータ条件は保存する。共通prefix長や入力再利用率を独立して指定するフォームは未実装。繰り返し入力ではprefix cacheの影響を考慮する。

## 実行構成

Docker ComposeにGuideLLM専用のCPU runnerサービスを追加済み。
Routerは対象の排他管理・認証・履歴・共通APIを担当し、runnerは固定バージョンのGuideLLM実行を担当する。
Routerコンテナへ試験用の重い依存関係を混在させず、Docker socketも共有しない。
runnerのジョブ受付は内部用とし、認証されたRouterからだけ受け付ける。

- 実行前に対象を試験中にし、既存要求の終了を待つ。待機要求の扱いは現在の試験時ポリシーを引き継ぎ、画面に示す。
- 直接接続では推論サーバ自体を測定する。Router経由では通常のHTTP経路とCapacity・キューを含めて測定する。
- Router経由では試験専用の一時認証とrun IDで対象試験を識別し、一般要求と区別して試験中の受付を許可する。試験終了で認証を失効させる。
- 直接接続の各要求はGuideLLMの結果で管理する。Routerを通過していない要求にRouterのキュー待ち時間を付けない。
- 実行状態は準備中／既存処理待ち／実行中／停止中／完了／失敗／中断を共通化する。
- 手動停止では子プロセスを含めて停止し、キャンセル済みの途中結果も保存する。
- Router／runner再起動時は残存ジョブを照合する。自動再実行はしない。上流の処理残存が確認できなければ対象を保留し、即座に通常受付へ戻さない。

「負荷投入時間」と「応答待ちタイムアウト」は別物とする。負荷投入終了後は実行中の応答を待つ。
GuideLLM側のHTTP待ち時間・終了制約が長文prefillや長時間生成を途中終了させない設定／連携を実装検証する。
単にCLI引数を付けるだけで保証せず、採用版のdrain・停止動作を確認する。

## 結果画面

| 表示区分 | 内容 |
| --- | --- |
| 実行条件 | エンジンと版、モデル、Tokenizer、データ識別情報、経路、負荷条件、生成設定 |
| 進捗 | 現在段階、経過時間、完了・失敗件数、取得可能な途中集計。取得できない指標は空欄 |
| 段階別結果 | 実際の同時実行条件・到着率、要求数、成功・失敗・キャンセル、要求/s、入力・出力token/s |
| 遅延 | TTFT、E2E、TPOT、ITLの分位点。取得できる指標のみ表示し、定義・単位・集計対象を保持 |
| 入出力 | 設定した長さと実測トークン数の分布。EOS等の個別終了理由は未保存 |
| リソース | 試験時間に対応するGPU・VRAM・RAM・サーバ指標。試験中に他プロセスが使う資源も含まれ得る |
| 比較・出力 | 過去試験との並列比較、条件差の表示、JSON／CSV／HTML出力 |

GuideLLMの集計を独自の近似値へ置き換えない。共通指標へ対応できない情報はエンジン固有結果として保持する。
異なるエンジン間で指標定義が違う場合は無条件に同列比較しない。
HTMLはダウンロードまたは隔離した表示にし、管理画面の権限で任意スクリプトを実行させない。

## 保存と拡張点

共通レコードにはrun ID、engine ID／version、設定schema version、対象、状態、時刻、段階別指標、成果物参照を保存する。
エンジン固有設定と結果は別のJSON領域に保存し、再実行時にも設定の版を検証する。

追加エンジンが提供するものは次に分ける。

1. メタ情報と機能一覧、設定schema、フォーム定義（必要なら専用のフォーム部品）。
2. 設定検証・実行前確認。
3. 開始・進捗取得・停止・再起動後の照合。
4. 結果の取り込み、共通指標への対応、エンジン固有の結果表示。

試験一覧・対象選択・認証・排他・履歴・成果物管理は共通基盤を利用する。
初期の選択肢はGuideLLMのみ。独自試験を追加する場合も、任意スクリプトのアップロードではなく実装済みadapterを登録する。

APIキーと入力・出力本文は結果、履歴、ログ、エクスポートに保存しない。
GuideLLMの既定出力は本文を含むため、本文サンプルを無効にし、成果物にも残らないことを検証する。
取り込んだ試験用データファイルは結果履歴と分けて管理し、明示的に登録したデータとして削除できるようにする。

## 移行工程と確認範囲

1. 完了（CPU・模擬HTTP）: GuideLLMの固定版で互換性検証：トークン計数、長い応答待ち、drain、停止、結果形式、本文非保存。
2. 実装済み: 共通試験モデル・adapter・runner・履歴の移行を実装する。
3. 実装済み: GuideLLMフォーム、進捗・停止、結果・比較・設定複製・エクスポートを実装する。
4. 一部確認済み: アプリを通じて直接接続／Router経由、長文、EOS、キャンセル、異常終了・再起動、データセットを検証する。

工程4の実GPU確認は直接／Router経由を各2要求。長い応答待ちや停止は模擬HTTPで確認し、新エンジンでの120k長文・公開HFデータのネットワーク取得は未実施。

既存の自作試験は新規実行の入口から外し、旧エンジンの測定値として履歴閲覧を残す。
過去の測定結果をGuideLLM結果へ変換したり、同じ条件で測ったように表示したりしない。
登録済みの接続先のみ対象とし、新しい推論サーバの登録やCapacity変更はこの統合に含めない。
