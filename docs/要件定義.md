# LLM Router 要件定義

更新日: 2026-09-19

基本方針と提示済み推奨案はユーザー了承済み。本書は追加条件を反映した要件ベースライン。未指定の実装詳細と残る検証事項は [要件確認事項](要件確認事項.md) で管理する。

## 1. 目的

研究室・組織内のGPUサーバで独立稼働するLLM推論サービスを一元管理する。利用者は個別サーバの接続先を意識せず、Routerにモデルのエイリアスを指定して推論を依頼する。

Routerは稼働状態・利用量・推論性能を継続的に収集し、負荷試験で把握した処理能力に基づいてリクエストを待機・転送する。過負荷による推論サーバ停止のリスクを下げることが目的であり、同時実行数の制御だけであらゆるOOMや障害を防げると保証するものではない。

## 3. 利用者と責任範囲

役割:

- 利用者: Router API Keyを使い、エイリアスを指定して推論を実行・キャンセルする。
- 管理者: 接続先・認証情報・利用者・処理能力を管理し、監視と負荷試験を行う。

管理画面は管理者ログイン必須。利用者API Keyでは管理操作不可。一般利用者向けポータル・モデル別アクセス権限は未実装。

Routerの対象はEndpoint登録、エイリアス解決、API認証、推論中継、キュー、キャンセル、稼働監視、利用量・性能記録、負荷試験。Web Dashboardはこれらを操作・確認する手段として提供する。

初期の対象外:

- 推論プロセスの起動・停止・再起動、モデルのダウンロード／ロード操作、上流API Key自体の変更。
- 同一モデルの複数サーバへの負荷分散、自動フェイルオーバー。
- 優先度による割込みや優先キュー。

トークン量に応じた重み付き実行制御は将来候補。課金、学習、外部公開、Routerの多重化は今回の合意には含まれない。

## 4. 管理対象

DBテーブルを確定するものではなく、混同を避けるための用語定義。

| 概念 | 内容 |
| --- | --- |
| Server | 物理サーバ。名前、ホスト、GPU等の資源情報を持つ |
| Endpoint | 推論サービスの接続単位。所属Server、backend種別、Base URL、認証情報を持つ。1 Serverに複数登録可能 |
| Model | 上流が受け付ける実際のモデル識別子 |
| Model Alias | 利用者向けの一意な名前。Endpointと上流モデル識別子を解決する |
| User / API Key | 利用者とその認証手段。複数キーを許す場合も公平性・利用量はUserに集約する |
| Request | 1回の推論要求。利用者、対象、状態、時刻、結果、計測値を持つ |
| Metric | Router、Endpoint、Serverそれぞれの観測値 |
| Benchmark / Capacity | 試験条件・測定結果と、管理者が設定した同時実行数 |

同一Endpointの複数モデル／AliasはEndpointの実行枠を共有する。同じGPUを複数Endpointが共有する場合の追加制御は別途設計する。エイリアスの一意性は、Endpointとエイリアスが1対1であることまでは意味しない。

## 5. 機能要件

この節は確定要件を具体化したもの。実装方式は[実装設計](実装設計.md)、確認済み範囲は[実装・検証状況](実装・検証状況.md)を参照。

### 5.1 登録とルーティング

- Server、Endpoint、上流モデル名、Aliasを登録・更新し、対象の利用を有効／無効にできる。
- Aliasの重複を拒否し、要求の`model`を登録された上流モデル名に変換して転送する。
- 未登録Aliasは明示的なエラーとし、別モデルに勝手に振り替えない。
- 稼働監視では登録情報と観測した状態、最終確認時刻を分けて表示する。登録済みモデルを「ロード済み」と断定しない。
- 接続不能、認証失敗、モデル不一致を区別する。初期値は10秒間隔、連続3回失敗で不健全、2回成功で復旧とし、調整可能にする。
- 無効化・削除・設定変更時の待機中／実行中リクエストの扱いは実装設計のRegistry変更規則に従う。

### 5.2 利用者向けAPI

初期必須は`GET /v1/models`、`POST /v1/chat/completions`とtool calling。通常応答とStreamingの両方に対応する。旧`POST /v1/completions`は初回必須範囲に含めていない。

- Bearer形式のRouter API Keyで利用者を識別する。
- `/v1/models`では有効な登録Aliasを案内する。Endpointの健康状態による絞込みは行わず、推論成功の保証とはしない。
- 非Streaming応答とSSE Streaming応答に対応する。
- 互換対象とする入力パラメータ、応答形式、エラー形式を明示する。
- `tools`、`tool_choice`、指定された`parallel_tool_calls`、assistantの`tool_calls`、toolメッセージと`tool_call_id`を保持して中継する。Streamingの分割されたツール名・引数・ID等を欠落させない。上流が対応する形式を尊重する。
- ツールの実行と結果の送信はクライアントが担当し、Routerはツールを実行しない。
- コンテキスト長や生成長にRouter固有の値を設定しない。入力の切り詰め・要約や、`max_tokens`／`max_completion_tokens`等の補完・上書きをしない。省略時は上流の既定に任せ、上流の制約違反は明示的なエラーにする。
- 画像は対象外。構造化出力、音声、Embeddings、Responsesは初回必須範囲に含めていない。
- backendやモデルが未対応の要求を黙って変更せず、対応範囲に沿ってエラーにする。

### 5.3 キューと同時実行制御

- Endpoint単位の実行枠を設け、適用中の同時実行数を超える要求をRouterで待機させる。
- 同一User内は受付順FIFO、User間はRound-Robinで次の実行対象を選ぶ。公平性は実行機会に関するもので、GPU時間やトークン数の均等配分ではない。
- 既に実行中の要求は追い出さない。後から到着したUserの即時実行は保証しない。
- 同じUserがキーを増やしても実行順で有利にならないようUser単位に集約する。
- 新規到着要求が既存の待機列を追い越さないよう、実行枠への割当を共通のスケジューラで管理する。
- ユーザー指定どおり固定のキュー件数上限を設けない。待機期限は管理者が設定可能、既定は無期限とする（R-14）。資源枯渇時の動作は別途決定し、暗黙の件数上限を追加しない。
- Streamingは終了または中断処理の完了まで実行中として扱う。
- 未試験時は管理者が暫定Capacity=1を確認して有効化する。減少時は実行中要求を追い出さない。共有GPUを使う複数Endpointの総容量は管理者が配分する。

### 5.4 キャンセルと障害

- 待機中のキャンセルは転送対象から除外する。
- 実行中のクライアント切断を検知し、上流接続の中断を伝播する。backendごとの推論停止の実効性を検証する。
- 切断によるキャンセルに加え、本人と管理者がrequest_idを指定して取り消すAPIを提供する。内部IDは応答ヘッダーで返し、応答前の取消にはクライアント指定IDも使用できる。
- 完了・失敗・タイムアウト・キャンセルを区別し、状態確定と実行枠解放の重複を防ぐ。
- Streaming開始前のエラーと開始後の異常終了を分けて定義する。
- 上流への再送は重複推論につながるため、初期は自動再試行しない。
- 不健全なEndpointへの新規転送を停止し、待機要求は理由付きエラーで終了する。Router再起動時は待機接続を引き継がず、設定と実績は永続化する。
- 初期は1台・1つのSchedulerで運用する。上流接続の確立期限は5秒を初期値とする。接続後の最初の応答待ちにタイムアウトを設けない。Streaming無通信・生成全体にもRouter独自の時間上限を設けない。HTTPクライアントや中継設定の既定値で意図せず打ち切らないようにし、切断・明示キャンセル・通信エラーは別途処理する。

### 5.5 認証情報と利用量

- Router API Keyと上流接続Credentialを分離する。
- Router API Keyはハッシュで保存し、発行時以外は平文を表示しない。失効・再発行を提供する。
- 上流Credentialは送信時に必要なためFernetで暗号化し、環境変数または所有者限定ファイルで鍵を管理する。認証不要の接続先も表現する。
- API Keyや上流Credentialをログや通常のAPI応答へ出さない。
- リクエスト件数・結果・入出力トークン数をUser、Alias、Endpoint、期間で集計する。
- トークン数を取得できない場合は不明として記録し、0使用と区別する。
- 通常要求のプロンプト／生成本文は履歴に保存しない。明示的に登録した試験入力ファイルは本文を含む別資産として保存する。ツール定義・引数・実行結果も本文として保存対象外とする。要求明細30日、1分集計90日、試験結果は手動削除まで保持し、期間を設定可能にする。

## 6. 監視・測定項目

測定項目はR-11の委任に基づき選定した。計測可能性は実機で検証する。保持期間・取得頻度の初期値は本書と決定記録に記載する。

### 6.1 リクエスト単位

記録項目: request_id、user_id、alias、endpoint_id、Streaming有無、受付・キュー投入・上流転送・終了時刻、最終状態、HTTPステータス、エラー種別。

| 指標 | 定義／扱い |
| --- | --- |
| Router待機時間 | キュー投入から上流転送まで。未転送で終了した場合は終了までの待機時間を別に扱う |
| E2E latency | Router受付から応答終了まで。失敗・キャンセルと成功は分けて集計 |
| 上流処理時間 | 上流転送から上流応答終了まで。純粋なGPU実行時間ではない |
| Router観測TTFT | 上流転送から最初の生成内容を含むイベントまで。受付起点のTTFTも別名で記録可能 |
| 入出力トークン数 | 上流のusage等を優先。取得元と欠測を区別する |
| 生成速度 | 使用するトークン数と時間区間を明示して算出。算出不能は欠測 |
| TPOT / ITL | backendまたはベンチマークが測定できる場合に収集。RouterのSSEチャンク間隔をそのままトークン間隔としない |

非Streamingでは通常、Routerだけから最初のトークン生成時刻を観測できない。TTFT・生成時間をE2Eから推測して埋めない。キャンセルでusageが返らない場合も欠測を保持する。

### 6.2 時系列・集計

- リクエスト到着数／完了数、毎秒／毎分件数、実行中数、待機中数。
- 入出力トークンスループット、待機時間、TTFT、E2EのP50／P95／P99。
- 成功率、エラー率、タイムアウト率、キャンセル率。各分母と集計窓を定義する。
- User／Alias／Endpoint別に集計し、通常利用と負荷試験を識別する。
- 率や分位値は対象期間・標本数・欠測状況とともに表示する。

Router観測値とbackend固有値は別系列にする。vLLMのメトリクス収集は追加情報として扱い、Router待機と上流内の待機を混同しない。

GPU利用率、VRAM使用量／総量、温度、消費電力、CPU、RAMは取得可能な環境で収集する候補。Router指標は必須とし、ハードウェア指標は取得可能な環境から追加する。付属Exporterと接続方法はDocker運用・運用手順に記載する。

### 6.3 Dashboard

- 一覧: Server／Endpoint／モデルの登録情報と稼働状態、実行中数／適用Capacity、待機数。
- 詳細: 期間指定したリクエスト量、トークン量、待機時間、遅延、エラー、取得可能なハードウェア指標。
- 管理: Endpoint／Alias／利用者／キー、負荷試験の条件・進捗・結果・Capacity適用。

画面更新は初期5秒周期。管理者向け画面を初期対象とし、一般利用者向け画面は別途整理する。保持期間は第5.5節に従う。

白黒グレーの共通デザインとし、一覧は表、詳細は項目行・タブ・グラフを基本とする。カード状の箱やKPIタイルを多用しない。状態は文字・記号でも区別する。具体的な画面と確認基準は [UI設計方針](UI設計方針.md) に従う。

## 7. 負荷試験とCapacity

- 新規試験はGuideLLM 0.7.3をCPU用runnerで実行する。旧独自エンジンは履歴閲覧用に保持する。操作・方式は[GuideLLM運用](GuideLLM運用.md)に従う。
- Endpointへの直接試験で推論サービスの能力を測り、Router経由の試験でキュー・認証・中継を含む動作を測る。結果を混同しない。
- 短入力×短出力、長入力×短出力、短入力×長出力、長入力×長出力を試験条件の候補とする。データ、Tokenizer、出力長、負荷方式、要求数または投入時間を試験ごとに指定する。
- 同時実行数または到着RPSを段階的に増加させ、スループット、遅延、エラー、取得可能な資源指標を保存する。
- 試験日時、Server／Endpoint／モデル、backendとツールのバージョン、試験条件、成功／失敗／中止、結果を再現可能な形で記録する。
- 同時実行数・入力長・出力長等の試験条件ごとに、スループット、TTFT、TPOT、E2E、エラー数等の測定値を表示する。合格基準、SLOによる合否判定、推奨同時実行数の算出は実装しない。
- 管理者が測定値を読んで同時実行数を入力・適用する（R-13）。試験完了だけでは運用中のCapacityを変更しない。
- 未試験時は管理者が暫定Capacity=1を確認して有効化。構成変更時は再評価する。保守時間に1→2→4…と試験し、要求エラー時は負荷段階の増加を中止する。OOM専用の分類・検知は実装していない。
- 長文入力とtool callingを実機検証に含める。試験用の長さ設定は通常要求へ流用しない。既存直接利用は順次統合する前提であり、専用の負荷追跡や全員の統合完了を開発の前提にしない。

## 8. 受入条件

以下は受入基準であり、全モデル・全環境での実機検証完了を意味しない。確認方法と未検証範囲は実装・検証状況に記録する。

| ID | 関連要件 | 確認する振る舞い |
| --- | --- | --- |
| AC-01 | R-01〜04, R-07 | 同一Serverの異なるEndpointを登録でき、重複Aliasを拒否し、Alias指定で正しい上流モデルに届く |
| AC-02 | R-05〜06 | 合意した互換クライアントで通常／Streaming要求が成功し、無効キーは上流へ転送されない |
| AC-03 | R-08〜09 | Capacity=CのときRouterから対象への実行中要求がCを超えず、超過分が待機する |
| AC-04 | R-08 | 複数Userが待機する状況でUser内FIFOと合意した公平性が成立する。Round-Robinの次回巡回で別Userにも実行機会がある |
